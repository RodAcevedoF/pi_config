# Personal Pi preferences

## Commit authority

- The user makes commits by default. Do not commit or amend without explicit user authorization, including during large ODD implementations. ODD work-unit guidance is not commit permission.
- Commit-format preferences describe how an authorized commit must look; they do not authorize creating one.
- Preserve existing staged and unstaged work. Do not stage, unstage, or otherwise alter the index without explicit user authorization.

## Commit messages

- Follow the repository's established ticket prefix and commit convention. Ask if the ticket or convention is unclear; never invent a ticket.
- Keep commits small and cohesive, with short messages.
- A typical subject is `AT-098 fix: <message>`; `AT-098` is an example, not a default ticket.
- When multiple related changes need detail and the repository permits it, use this structure:

```text
AT-098 fix:
- message
- message
refactor:
- message
- message
```

- In `jaspy-monorepo`, follow its stricter convention: `JPD-<ticket> <type>: <short message>`, for example `JPD-123 feat: <message>`. Do not assume the multiline form is permitted there.
- Do not add `Co-authored-by`, `Generated by`, agent signatures, or other AI attribution to commit messages.

## Local ODD tracking

- Keep `odd/` tracking documents local and untracked. Respect the global Git exclusion; do not force-add them to commits.

## Session handoff

- When the user wants to continue in a new session and work is in progress (for example "abrimos nueva sesión", "seguimos en otra sesión", "dame un prompt para la siguiente sesión", or a context-size reason), write a continuation prompt to `odd/handoff.md` at the project root, replacing the previous one, without being asked for the file. Start it with the date, branch, and working directory, and keep it self-contained: done, pending, decisions, and how to verify.
- Reply with the prompt and its path; the user can then start the next session with `Read odd/handoff.md and continue.`
- Read `odd/handoff.md` only when the user points to it. It is a snapshot, not live state: check it against git and the code before acting.
